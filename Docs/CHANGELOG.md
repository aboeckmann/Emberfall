# Project Emberfall — Changelog

Every major design decision gets recorded here.

---

## 2026-07-04

**Renamed Initiative to Balance and made it a single shared meter starting at 50 (neutral).**
Reason: "Balance" better expresses what the meter is — control of the fight as a tug-of-war between both sides — and starting at 50 makes neutral the explicit default, with neither side advantaged at the opening bell. Previously each combatant carried their own 0-100 Initiative score starting at 0; now one meter lives on the encounter itself: 100 = player in full control, 0 = enemy in full control. Consequences: the free-bonus-action threshold moved from >=50 to >=75 (with a 50 start, the old threshold would have triggered immediately — the reward should require earned advantage), and the Dire Wolf's Howl now slams the shared meter to 0 instead of setting its own score to 100. Deltas unchanged (+10 hit landed / +15 Parry / +5 Dodge / -15 hit taken). The bonus action and enemy low-Balance payoffs remain unimplemented — the meter is still informational in the encounter loop. Combat HUD now labels the bar "Balance" and annotates who holds the advantage.

**Built the first playable screen: a functional combat HUD over the encounter loop.**
Reason: the encounter loop could only be exercised headlessly; playtesting the combat feel — the entire point of the Prototype — requires a screen. Added `scenes/combat/combat_screen.tscn` + `.gd` (now the project's main scene): portrait 720x1280 with Container-based layout and the default Godot theme, surfacing enemy HP + telegraphed intent, a scrolling combat log, player HP/Stamina/Initiative bars, position buttons, and the five combat actions, with restart-vs-Wolf/Dire-Wolf buttons at fight's end. Deliberately a functional scaffold, not designed UI — Art Direction (`12_Art_Direction.md`) doesn't exist yet, so no visual-style decisions were made. Position options are Frontline/Balanced/Guarded only, since Flanking requires groups and Rear is encounter-specific per `04_Combat_Design.md`, neither of which the single-enemy Prototype has. Mana/Focus aren't displayed (no caster in scope). Removed the placeholder `Main.tscn`. The screen script contains no game rules — it only forwards button presses to `CombatEncounter` and renders state, per the logic/presentation separation rule. Verified headlessly with a smoke test that drives the screen's actual buttons through a full fight (53 checks total, all passing).

**Implemented the turn-by-turn combat encounter loop (`CombatEncounter`), and formalized defense resolution.**
Reason: the rules layer had all the individual formulas (damage, threat, initiative) but nothing that actually ran a fight round by round. Added `EnemyIntent` and `CombatEncounter`, which implement the telegraph-then-resolve cadence from `04_Combat_Design.md` ("Observe -> Respond"): a Wolf circles for 2 rounds, then alternates TELEGRAPHING_BITE -> BITE every other round; Dire Wolf telegraphs Howl at the fight's start and again the first time it crosses 50% HP, seizing full Initiative when it resolves. Also formalized **Defense Resolution**, which nothing in the Balance Bible had specified: Parry/Dodge fully negate a resolving Bite (Parry only if the weapon's `can_parry` is true), Guard reduces it by 50% (further reduced by the low-Stamina penalty), and choosing to attack instead of defend takes the full hit — documented as a first-pass, no-separate-roll design in `11_Balance_Bible.md`. Corrected `Combatant.spend_stamina` from a hard action-blocking gate to a floor-at-0 deduction, since the design only specifies a soft low-Stamina penalty, not unavailable actions. Circling/retreating are implemented as plain round counters rather than a spatial/cornering system — "re-engages if cornered" is simplified to "retreat always expires after 3 rounds" (a new first-pass number for the Balance Bible's "several rounds"). Verified with 13 new checks in `tests/run_tests.gd` (46 total, all passing), including a full fight run to completion.

**Implemented the Prototype's rules layer in GDScript: Core Attributes, Skill Gain, Sword/Wolf combat math, and Character Creation.**
Reason: every number needed already existed in `11_Balance_Bible.md`; this is the first real code, translating those formulas into the engine-agnostic `game/` layer per the logic/presentation separation rule in `02_Technical_Design_Document.md`. Added `Attributes`, `Skill` (level curve + bucket gain/drain), `SkillGainTable`, the `EquipmentData`/`WeaponData`/`AppearanceData` schema plus a `sword.tres` instance, a new `EnemyData` schema (not previously documented — added to the TDD) plus `wolf.tres`/`dire_wolf.tres` instances, `CombatPosition`/`CombatAction`/`StaminaRules`/`DamageCalculator`/`ThreatAndInitiative`/`Combatant` for the combat math, and `CharacterSheet` implementing the Prototype-minimal creation flow. Verified with a minimal ad-hoc GDScript check script (`tests/run_tests.gd`, 33 checks, no test framework chosen yet) run headlessly against Godot 4.7 — all passing. Enemy AI behavior (circling, retreat timing, Howl/Enrage triggering, the Wolf's Emboldened state) is explicitly not implemented yet; only the pure stat-check rules are (`game/enemies/enemy_rules.gd`) — the turn-by-turn encounter loop is a separate future task.

**Defined the equipment data schema (Prototype scope: the Sword only).**
Reason: `09_Economy_And_Crafting.md` established the Gameplay Data / Appearance Data split conceptually but never gave it concrete fields, so there was nothing to build the Sword against. Added `EquipmentSlot`, `EquipmentData`, `WeaponData`, and `AppearanceData` schemas to `02_Technical_Design_Document.md`, modeled as Godot `Resource` subclasses per the existing `data/` folder convention. `WeaponData` includes `stamina_cost_modifier` and `can_parry` as hooks for future Weapon Feel differentiation (Great Axe, Bow, etc. per `04_Combat_Design.md`) even though only the Sword exists right now, since those fields are direct implications of already-documented design rather than new speculation. Armor's schema is deferred — no armor exists in Prototype scope. Concrete Sword values recorded in `11_Balance_Bible.md`.

**Defined a Prototype-minimal character creation flow, and fixed a contradiction in the guild-start rules.**
Reason: `06_Guilds.md` and `01_Game_Design_Document.md` both said "players do not begin in a guild" and "players begin with one active guild" in the same breath. Resolved in favor of guildless start — guilds require minimum skill levels and an initiation quest, neither of which a level-0 character can satisfy, so the Prototype's one guild is earned through play rather than granted at creation. Character creation itself (`03_Game_Systems.md`) is scoped to Prototype-minimal: name entry, a fixed placeholder attribute spread (Intellect/Vitality/Willpower 10/10/10), all skills at 0, guildless, auto-equipped with the Sword, 0 Renown, dropped into the Bastion at Ember tier. No attribute allocation UI or appearance customization yet — both remain open questions pending the real attribute-assignment method and Art Direction.

**Chose Dire Wolf (a boss version of the Wolf) as the Prototype's boss, and defined the full Core Attributes trio (Intellect, Vitality, Willpower).**
Reason: the Roadmap requires one boss for the Prototype and none was chosen. Reusing the Wolf's template kept scope small — Dire Wolf adds one new ability (Howl, which seizes Initiative outright) and drops the regular Wolf's circle/retreat behavior so it reads as a boss rather than a reskinned trash mob, without requiring new AI systems. Separately, completed the Core Attributes concept started with Intellect: Vitality now backs max HP/Stamina and Willpower backs max Mana/Focus, giving every resource pool in the combat system a consistent attribute-driven source instead of a flat number. Attributes are assigned at character creation, but character creation itself doesn't exist yet and attribute growth over time is undecided — both tracked as open questions in `01_Game_Design_Document.md`. A flat placeholder spread (10/10/10) is used for Prototype development in the interim. See `11_Balance_Bible.md`.

**Defined skill gain as a bucket system, and drafted first-pass combat/skill numbers for the Prototype (Sword vs. Wolf).**
Reason: skill gain, Practice, and Rest were all TBD placeholders with no mechanical relationship to each other. Bucket system: actions fill a per-skill XP bucket (sized by a new Intellect core attribute) rather than granting skill XP directly; the bucket drains into real skill XP passively everywhere, faster while Resting at the Bastion. This gives Rest and Practice concrete mechanical purpose and creates a play rhythm (adventure to fill buckets, return home to convert them) without hard-blocking play when a bucket is full. Also finalized Prototype-scope numbers (Stamina costs, Sword damage formula, Threat/Initiative formulas, Wolf stats) so combat code has real values to implement against — see `11_Balance_Bible.md`. All numbers are explicitly first-pass and expected to change after playtesting. The Prototype's boss is still unchosen.

**Chose the tech stack: Godot 4.x + GDScript, local JSON saves for the Prototype, backend deferred.**
Reason: Emberfall is a UI-heavy 2D tactical RPG and Godot's 2D/UI tooling is first-class; GDScript is the fastest ramp for a scripting background; free and lightweight. Unity's advantages (3D pipeline, mobile LiveOps ecosystem) aren't needed yet. Backend (PlayFab vs Firebase vs custom) is deliberately deferred until a milestone needs server-authoritative progression. Adopted a standing architecture rule: game rules never call engine APIs, keeping formulas headless-testable and the engine swappable. See `02_Technical_Design_Document.md`.

**Changed combat from free movement to tactical positioning.**
Reason: Better supports deliberate gameplay — players win by making better decisions, not by moving/tapping faster.

**Split the single GDD into a modular `/Docs` structure (00–14 + Changelog).**
Reason: The master document was becoming unwieldy — it mixed stable vision content with fast-changing balance numbers and unwritten content/tech sections. Splitting keeps `01_Game_Design_Document.md` stable while `11_Balance_Bible.md` and `10_Content_Bible.md` can change constantly without touching the rest.
